## Defect A — HIGH: `pipe_run_dynamic` Passes `nodes_json` as Unquoted Shell Argument

### Location
`.pi/extensions/context-pipe.ts` line 102 + `callCli` lines 14–26.

### Code
```typescript
async execute(_toolCallId, params) {
  return callCli(["run-dynamic", params.nodes_json], params.input_text);
}

// callCli:
const cmd = `"${mcpPipePath}" ${args.join(" ")}`;
return execSync(cmd, { input, encoding: "utf-8" });
```

### Problem
`nodes_json` is a JSON string like `[{"cmd":"grep","args":["ERROR"]}]`. When spliced into the shell command string via `args.join(" ")`, the result is:

```
"mcp-pipe" run-dynamic [{"cmd":"grep","args":["ERROR"]}]
```

`execSync` runs this through `cmd.exe` on Windows. The unquoted double-quotes in the JSON are consumed by the shell, fragmenting the argument into multiple tokens. Python's `argparse` receives the first fragment (`[{`) as the `nodes_json` positional argument, which fails `json.loads()` with `JSONDecodeError`.

Confirmed by simulation:
```
cmd: mcp-pipe run-dynamic [{"cmd":"grep","args":["ERROR"]}]
shell splits to: 'mcp-pipe', 'run-dynamic', '[{', 'cmd', ':', 'grep', ...]
```

### Fix
**Do NOT use string escaping.** Backslash-escaping (`replace(/"/g, '\\"')`) works on Unix `sh` but is wrong on Windows `cmd.exe`, which does not honour `\"` as an escape sequence. The correct cross-platform fix is to replace `execSync` with `spawnSync` in `callCli`, passing arguments as an array so the shell is bypassed entirely:

```typescript
import { spawnSync } from "child_process";

const callCli = (args: string[], input?: string) => {
  // Fast path: mcp-pipe binary via spawnSync (no shell, args array is safe)
  const result = spawnSync(mcpPipePath, args, { input, encoding: "utf-8", maxBuffer: 50 * 1024 * 1024 });
  if (result.status === 0) return result.stdout;
  // Fallback: python module
  const result2 = spawnSync(pythonExe, ["-m", "context_pipe.cli", ...args], { input, encoding: "utf-8", maxBuffer: 50 * 1024 * 1024 });
  if (result2.status === 0) return result2.stdout;
  throw new Error(result2.stderr || "CLI call failed");
};
```

This also resolves **Defect C** (maxBuffer) in a single change.

## Defect B — HIGH: `pipe_analyze_file` Reads Full File Instead of Stat

### Location
`.pi/extensions/context-pipe.ts` lines 85–91.

### Code
```typescript
pi.registerTool({
  name: "pipe_analyze_file",
  description: "Analyze a file through the context pipe with semantic analysis.",
  ...
  async execute(_toolCallId, params) {
    const text = readFileSync(params.path, "utf-8");                          // ← reads FULL file
    return callCli(["run", params.pipe_name || "semantic-refinery"], text);   // ← pipes full content
  }
});
```

### Problem
The MCP `server.py` implementation of `pipe_analyze_file` is a **lightweight stat operation**:

```python
size = os.path.getsize(resolved_path)
recommendation = "standard-distill" if size <= 10000 else "semantic-refinery"
return f"File: {os.path.basename(path)}\nSize: {size} bytes\nRecommendation: Use pipe_read_file with pipe_name='{recommendation}'."
```

It explicitly states: *"Analyzes a file's size and structure to recommend the optimal context pipe, **without flooding the context window**."*

The extension template does the opposite — it reads the **entire file** into memory and pipes the full content through `semantic-refinery`. This:

1. **Defeats the tool's purpose** — returns sifted content instead of a recommendation string
2. **Can flood the context window** — the very thing it exists to prevent
3. **Compounds REPORT_034** — also returns a raw string (not `{ content: [...] }`)
4. **Hits Defect C's maxBuffer limit** for large files (see below)

### Fix
Replace `readFileSync` + `callCli` with a stat-only operation:
```typescript
async execute(_toolCallId, params) {
  const { statSync } = require("fs");
  const { basename } = require("path");
  const size = statSync(params.path).size;
  const recommendation = size > 10000 ? "semantic-refinery" : "standard-distill";
  return {
    content: [{ type: "text", text: `File: ${basename(params.path)}\nSize: ${size} bytes\nRecommendation: Use pipe_read_file with pipe_name='${recommendation}'.` }]
  };
}
```

## Defect C — MEDIUM-HIGH: `execSync` Default 1 MB `maxBuffer` — Large Outputs Silently Fail

### Location
`callCli` function, lines 14–26.

### Code
```typescript
const callCli = (args: string[], input?: string) => {
  try {
    const cmd = `"${mcpPipePath}" ${args.join(" ")}`;
    return execSync(cmd, { input, encoding: "utf-8" });  // ← no maxBuffer
  } catch (e) {
    try {
      const cmd = `"${pythonExe}" -m context_pipe.cli ${args.join(" ")}`;
      return execSync(cmd, { input, encoding: "utf-8" }); // ← no maxBuffer
    } catch (e2: any) {
      throw e2;
    }
  }
};
```

### Problem
Node.js `execSync` defaults to `maxBuffer: 1024 * 1024` (1 MB). Confirmed:
```
default maxBuffer: 1048576 bytes (1MB)
large output would throw: RangeError: stdout maxBuffer length exceeded
```

Context-pipe is specifically designed for **large files** (the lab has a `heart-attack-pipe` scenario that handles giant files). Any sifted output exceeding 1 MB throws `Error: spawnSync ... stdout maxBuffer length exceeded`, caught by the inner `catch` and re-thrown to pi's tool dispatch as an unhandled error.

A 1 MB limit is fundamentally incompatible with the tool's stated purpose of handling large context reads safely.

### Fix
Pass an explicit `maxBuffer` large enough for expected outputs:
```typescript
return execSync(cmd, { input, encoding: "utf-8", maxBuffer: 50 * 1024 * 1024 }); // 50 MB
```
Apply to both the fast-path and fallback `execSync` calls.

## Defect D — MEDIUM: `tool_call` Interceptor Only Notifies — Does Not Block Native `read`
> ⚠️ **Scope note:** The pi.dev implementation defect is described here. The universal mandate-enforcement gap across ALL platforms has been split to **REPORT_036**.

### Location
`.pi/extensions/context-pipe.ts` lines 107–118.

### Code
```typescript
pi.on("tool_call", async (event, ctx) => {
  if (isToolCallEventType("read", event)) {
    const filePath = event.input.path;
    try {
      const stats = statSync(filePath);
      if (stats.size > 1024) {
        ctx.ui.notify("Large file detected. Redirecting to pipe_read_file.", "info");
      }
    } catch (e) {}
    // ← returns undefined — native read still executes
  }
});
```

### Problem
Per `extensions.md`, the `tool_call` handler can only block by returning `{ block: true, reason?: string }`. Returning `undefined` (as this handler does) has no effect — the native `read` tool executes normally.

The notification says *"Redirecting to pipe_read_file"* but no redirect occurs. The AGENTS.md mandate in this project explicitly states:
> **FORBIDDEN TOOLS**: native `read` tool for files > 1KB.

The extension advertises enforcement it doesn't provide.

### Fix
Return a block directive for large files:
```typescript
pi.on("tool_call", async (event, ctx) => {
  if (isToolCallEventType("read", event)) {
    const filePath = event.input.path;
    try {
      const { statSync } = require("fs");
      const stats = statSync(filePath);
      if (stats.size > 1024) {
        return {
          block: true,
          reason: `File is ${(stats.size / 1024).toFixed(1)}KB. Use pipe_read_file("${filePath}") instead.`
        };
      }
    } catch (e) {}
  }
});
```

## Defect E — LOW: `tool_result` `finally` Clears a Status That Was Never Set

### Location
`.pi/extensions/context-pipe.ts` lines 120–134.

### Code
```typescript
pi.on("tool_result", async (event, ctx) => {
  const text = event.content?.[0]?.text;
  if (typeof text === "string" && text.length > 5000) {
    if (text.includes("--- [Context-Pipe Audit] ---")) return;
    try {
      const sifted = callCli(["run", "standard-distill"], text);
      return { content: [{ type: "text", text: sifted }] };
    } catch (e) {
      console.error("[Context-Pipe] Auto-sift failed");
    } finally {
      ctx.ui.setStatus("context-pipe", "");  // ← clears a status never set
    }
  }
});
```

### Problem
`ctx.ui.setStatus("context-pipe", "")` clears a named status widget, but there is no preceding `ctx.ui.setStatus("context-pipe", "⚡ sifting...")` call before `callCli(...)`. The user never sees a visual indicator that auto-sift is running, and the `finally` is a no-op that clears nothing. This is a UX gap — for slow files, the session appears frozen with no feedback.

### Fix
Add the status set before the `callCli` call:
```typescript
try {
  ctx.ui.setStatus("context-pipe", "sifting...");
  const sifted = callCli(["run", "standard-distill"], text);
  return { content: [{ type: "text", text: sifted }] };
} catch (e) {
  console.error("[Context-Pipe] Auto-sift failed");
} finally {
  ctx.ui.setStatus("context-pipe", "");  // now correctly clears the status
}
```

## Cross-Platform Risk of These Fixes

**All five defects and their fixes are strictly confined to the `_inject_pi()` template in `onboarding.py`.** No other platform injector is affected:

| Fix | Scope | Risk to other platforms |
|---|---|---|
| **A** — `spawnSync` for `run-dynamic` | `_inject_pi()` template only | ✅ None — no other injector calls `run-dynamic` via subprocess |
| **B** — `pipe_analyze_file` stat-only | `_inject_pi()` template only | ✅ None — MCP `server.py` already correct; unrelated |
| **C** — `maxBuffer` 50MB | `_inject_pi()` template `callCli` only | ✅ None — other platforms use the MCP Python server (no buffer cap) |
| **D** — `tool_call` block | `_inject_pi()` template only | ✅ None — pi-specific API; see REPORT_036 for universal tracking |
| **E** — `setStatus` prior set | `_inject_pi()` template only | ✅ None — pi-specific API |

**One secondary note:** `_inject_openclaw()` also uses `execSync` at line 1162 of `onboarding.py` (passes payload via stdin, not shell args — no injection risk). It similarly lacks a `maxBuffer` override, but that is a separate issue outside the scope of this report.

**Onboarding re-run safety:** When the fixes land and `python -m context_pipe.onboarding` is re-run, the horizon scanner will regenerate configs for ALL detected platforms (Gemini, OpenCode, pi, etc.). Since only `_inject_pi()` changes, all other injectors produce identical output to today. No regression risk.
